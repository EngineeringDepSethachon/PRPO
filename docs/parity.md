## 0. ภาพรวมสถาปัตยกรรมที่กระทบ parity (อ่านก่อน)

1. **Business logic อยู่ที่ frontend (`wf.js`) ทั้งสองโหมด** GAS `api*` ทำหน้าที่ persist + side-effect (audit log, notification, budget tx, เลขเอกสาร, Drive) ; CF ปัจจุบันเป็น CRUD mirror ของ mock server ไม่มี side-effect เหล่านี้
2. **โหมด backend 3 แบบ** (`src/config/backendMode.js:11-42`): `mock` (`/api/*` express), `gas` (`google.script.run` ผ่าน `callGAS` `store.js:75`), `cloudflare` (`fetch /api/*` ไป CF)
3. **GAS ไม่มี server-side RBAC จริง**: `handleApiRequest` (`Code.gs:71-152`) สร้าง user จาก context ที่ client ส่งมา ถ้าไม่ส่งจะ default เป็น `role: 'ADMIN'`, `isAdmin: true` (`Code.gs:99,113-115`) ; ฟังก์ชัน `requireAuth/requireRole/requirePermission/requireDepartment` (`Code.gs:409-463`) ถูก **ประกาศแต่ไม่ถูกเรียกจาก api* ใดเลย** (grep ยืนยัน) ดังนั้น "สิทธิ์ตามโค้ดเดิม" = ประตูฝั่ง client (`wf.canAction` `wf.js:54-155`, `resolveUserPermissions` `const.js:211-261`) เท่านั้น
4. **GAS ไม่บังคับ state machine ที่ server**: status ที่เขียนลงชีตส่วนใหญ่มาจาก payload ของ client ; GAS บังคับ/คำนวณเองเฉพาะ `apiApprovePR` (`APPROVED`, 1755), `apiCancelPR` (`CANCELLED`, 1886), `apiReceivePO` (`WAITING_DELIVERY_ROUND_2` / `COMPLETED`, 2769-2774), `apiCancelPO` (`CANCELLED`, 3764), `apiFinalizePO` (PR→`APPROVED`, 3200) — ดูหัวข้อ (a)
5. ชื่อฟิลด์ต่างกันระหว่างชีตกับ D1 (กระทบทุกแถวด้านล่าง ดูข้อ D-1..D-8 ในหัวข้อ (e))

## 1. ตาราง parity รายฟังก์ชัน

คำอธิบายสถานะ: **มี** = มี endpoint และพฤติกรรมใกล้เคียง ; **ต่าง** = มี endpoint แต่ logic/รูปข้อมูลต่าง ; **ขาด** = ไม่มี endpoint
รหัสในคอลัมน์สิทธิ์ (นิยามเต็มหัวข้อ (c)): **S0** = server ไม่ตรวจ (`Code.gs:71`) ; ตามด้วย gate ฝั่ง client
รหัสโน้ต `D-n` / `C-n` = ดูหัวข้อ (e)

จำนวน: GAS `api*` 67 ฟังก์ชัน (`gas/Code.gs`; `backend-gas/Code.gs` มี 67 เท่ากัน) + 1 ฟังก์ชันที่ frontend เรียกแต่ **ไม่มีใน GAS** (`apiGetImageBase64`) = 68 แถว ; มี 4 / ต่าง 43 / ขาด 21

### c.5 RBAC ฝั่ง server ที่บังคับแล้ว (T4.5: `functions/_lib/rbac.js`, `authorize` ใน `functions/api/[[route]].js`)

ไม่เพิ่ม/ลดสิทธิ์ — ยกกฎของ client เดิมมาบังคับที่ server ; ตารางจริงอยู่ใน `ENDPOINT_RULES` (ทดสอบใน `tests/cf_rbac.test.js`) :
- GET ทุก endpoint = ผู้ login ทุกคน (เหมือนเดิม) ยกเว้น `GET /api/audit-logs` = admin (หน้า `admin/audit-logs` เป็น SYSTEM_ADMIN)
- `/api/users` POST/PUT/DELETE, `/api/departments` เขียน = admin เท่านั้น (UserMasterView `isAdmin`, MasterDataView แท็บ departments) ; เปลี่ยนรหัสผู้ใช้/level/roleId ทำได้ผ่านทางนี้ทางเดียว (ระบบเดิมไม่มีหน้าเปลี่ยนรหัสตัวเอง)
- products/vendors/storage-locations/usage-units: เขียน = `canManageMaster`, ลบ = `canDeleteMaster` (level>=1 ตามที่ผู้ใช้ตัดสิน)
- `budgets/allocate`, `budgets/reset`, `POST /api/budgets` = admin หรือ level>=2 ที่ไม่ใช่ ONLINE_PURCHASER (`BudgetView.canAllocateBudget`) ; `budgets/adjust` ผู้อื่นทำได้เฉพาะ 3 action ที่ client ส่งจริง: `TOP_UP` (delta>0, ห้ามมี newAmount), `BUDGET_ROLLBACK` (delta>0), `BUDGET_DEDUCT` (delta<0) ; TOP_UP/ROLLBACK ปรับยอดแบบ relative ใน SQL (ไม่ read-modify-write)
- PO receive = `canReceiveGoods` (level 1 / admin) ; settle = `canOnlinePurchase || canCloseOwnPO` ; PR/PO เปลี่ยนสถานะ = ตาม `canAction` ของสถานะปัจจุบัน (DRAFT: ทุกคน, SUBMITTED-ชุดตรวจ: level 2 ไม่ใช่ online, REVIEWED: level>=3 ไม่ใช่ online, PO `IN_PROGRESS_ONLINE`: online/admin) ; สถานะอื่นเป็นงานระบบ เปิดให้ผู้ login

- **ยังไม่บังคับฝั่ง server (ระบบเดิมกรองที่ UI เท่านั้น)**: จำกัดแผนก (`allowedDepartments`/`hasDepartmentAccess`/`canAccessDepartmentData`), เจ้าของ PR (`isDocOwner` จับชื่อ), `disallowOnlinePurchaser` ของหน้า master-data/quick-issue/my-workspace, UserMasterView ห้ามลบ ADMIN/ตัวเอง (`UserMasterView.jsx:135`), ห้ามรับของเมื่อมีเคลมค้าง
- ความเสี่ยงที่คงตาม parity: ระดับ admin คำนวณเหมือน login (`level>=99`/username `admin`/ข้อความ `ADMIN` ใน roleId,canonicalRole,positionKey,title) — ใครมี title ที่มีคำว่า ADMIN จะเป็น admin ; กุญแจนี้แก้ได้เฉพาะ admin
- เส้นทาง: normalize ครั้งเดียวก่อน authorize+routing (ตัด `/` ท้าย ; ปฏิเสธ `//`, `%2f`, `%5c`, `%2e`, `%00` ด้วย 400) ; rule ทุกอันเป็น exact match ไม่มี `\/?$`
- `budgets/adjust` (T4.5 รอบ 2): `TOP_UP`/`BUDGET_ROLLBACK`/`BUDGET_DEDUCT` คำนวณจากสถานะใน D1 เท่านั้น (ตรง mock `server/routes/budgetRoutes.js`: TOP_UP เพิ่ม monthlyBudget ของเดือน, ROLLBACK ลด totalUsed + เพิ่ม refundCredits, DEDUCT เพิ่ม totalUsed) ไม่ใช้ `newAmount`/`previousAmount` ของ client ; ผู้ไม่มีสิทธิ์งบส่ง TOP_UP พร้อม newAmount ไม่ได้ (403) — ความเสี่ยงที่เหลือ: ผู้ปิดงานระดับ 1/online ส่ง TOP_UP delta สูงๆ ได้ เพราะ flow คืนเงินเดิมเรียกแบบนี้และ server ไม่รู้ที่มาของยอด

**ลายเซ็นไม่ทำให้ review/approve พัง**: ช่องลายเซ็นทุกคีย์ที่ลงท้าย `signature` (รวม `requesterSignature`) ถ้าไม่รองรับ (svg, bmp, ใหญ่เกิน 400k, URL ต่างโดเมน, scheme อันตราย) จะถูกตัดเป็น `''` ไม่ตอบ 400/413 ; แต่การ **บันทึกลายเซ็นผู้ใช้** (`POST/PUT /api/users`) เข้มกว่า: ต้องเป็น `data:image/(png|jpeg|webp)` ≤400k หรือ URL Drive มิฉะนั้น 400 ข้อความไทยให้อัปโหลดใหม่ (ค่าเดิมที่เก็บอยู่แล้วและไม่ถูกแก้ ไม่ถูกตรวจซ้ำ) ; หน้าจัดการผู้ใช้บีบรูปลายเซ็นที่อัปโหลดเป็น JPEG ≤ ~200KB ก่อนส่ง และไม่รับ SVG ; รูปเดโมของ `FALLBACK_SEED_ATTACHMENTS` เป็น SVG data URL — ในช่องไฟล์ถูกตัดเป็น `''` (ไม่ error) เมื่อบันทึกขึ้น CF

- **T4.6c settle ตาม GAS `apiSettlePO` (แก้แถว 42 / C-4)**: client (`POSettlementModal` → `apiService.settlePO`) ส่ง `actualTotalAmount / savingsAmount / actualItems / settlementNote / settlementProofUrl` — server **คำนวณ savings เอง ไม่เชื่อ `savingsAmount` จาก client**: `savings = (approvedTotal + ยอด BUDGET_DEDUCT ของ PO − ยอดที่ PO คืนไปแล้ว) − actualTotalAmount` (ถ้า PO ไม่มี snapshot `approvedTotal` ใช้ `grandTotal` เฉพาะแสดงตัวเลข ไม่คืนเงิน) ; savings > 0 → คืนผ่านเส้นทางเดิม (ledger `REFUND_SETTLEMENT` + เพดานร่วม + ผูก budgets กับ ledger) ถ้าเกินเพดานคงเหลือ **clamp เท่าที่เหลือ** ตอบ `refundClamped/refundRequested` (ใช้ทำเฉพาะกรณีที่ server คำนวณเอง; รูปแบบเก่าที่ส่ง `refundAmount` ตรง ๆ ยังตอบ 400 ถ้าเกิน) ; savings < 0 (จ่ายเกิน) → GAS ไม่คืนและไม่หักเพิ่ม ทำเหมือนกัน (เก็บ `savingsAmount` ติดลบ) ; ที่คืนไปแล้วก่อน settle (adjust ROLLBACK ตอนรับออเดอร์ออนไลน์ราคาลด, claim credit) ถูกหักออกจากฐาน จึงไม่คืนซ้ำ. ไม่มี `actualTotalAmount` → รูปแบบเดิม (`refundAmount`)
  - **status**: ไม่เปลี่ยน (เดิม CF ตั้ง `CLOSED`) ตั้งแค่ `settlementStatus='SETTLED'` ตาม GAS/client ; กันคืนซ้ำใช้ `settlementStatus` + ledger แทน status: settle ซ้ำ → `200 duplicate:true` ไม่เขียน/ไม่คืนซ้ำ (GAS เขียนทับได้แต่คืนงบครั้งเดียวต่อ PO — ที่นี่ปิดการเขียนทับ) ; settle พร้อมกันหลายคำขอ → ผู้ชนะเขียนผล+คืนงบครั้งเดียว (token ใน extraJson) ; ปรับเทสต์/e2e ที่คาด `CLOSED` เป็น `settlementStatus SETTLED` + status เดิม
  - **เก็บผล**: `pos.actualTotalAmount` (คอลัมน์จริง), `itemsJson` (ราคา actual ต่อรายการ), ที่เหลือใน `pos.extraJson`: `settlementStatus, savingsAmount (ค่าที่ server คำนวณ), settlementNote, settlementProofUrl (ผ่าน sanitize), actualItems, settledBy (จาก token), settledAt (เวลา server)` ; `GET /api/pos` และ `/api/bootstrap` ผสมฟิลด์เหล่านี้กลับเป็นฟิลด์ระดับบนสุดที่ client อ่าน (`settleToken` ภายในไม่ส่งออก)

- **T4.6d แก้ยอดจ่ายจริงหลังปิดยอด (ตัดสิน: ตรง GAS + คง UX)** — `PODetailsModal` มีปุ่ม "แก้ไขยอดจ่ายจริง" หลัง settle จึง `POST /api/pos/:id/settle` ซ้ำ **เขียนทับ** `actualTotalAmount / actualItems / itemsJson(ราคา actual) / settlementNote / settlementProofUrl / settledBy / settledAt / savingsAmount` (ผู้มีสิทธิ์ settle เท่าเดิม ; last write wins) และไม่ตอบ `duplicate` อีก (ตอบ `resettled:true`) ; client ไม่ต้องแก้. **งบ (ตรง GAS ทุกประการ — แก้ไขจากร่างก่อนหน้าที่คืนส่วนเพิ่ม ซึ่งเป็นคำสั่งของ Neo ไม่ใช่ผู้ใช้ตัดสินและเปลี่ยน business rule เดิม)**: คืนงบเฉพาะ settle **ครั้งแรก** ; settle ซ้ำ (แก้ยอด) เขียนทับฟิลด์ปิดยอดเท่านั้น **ไม่คืนเพิ่มและไม่ดึงงบกลับ** ไม่ว่า savings ใหม่จะมากหรือน้อยกว่าเดิม (GAS เรียก `apiAppendBudgetTransaction` BUDGET_ROLLBACK ซึ่งกันซ้ำด้วย type+docNo) ; ที่นี่กันซ้ำด้วย `REFUND_SETTLEMENT` ของ PO นั้นมีแล้ว (`NOT EXISTS` อยู่ในคำสั่ง INSERT ledger เอง จึงกัน race ของ settle พร้อมกัน) ; `savingsAmount` ที่เก็บ = ค่าที่คำนวณใหม่ตามยอดจ่ายจริงล่าสุดเสมอ (เขียนทับเหมือน GAS) โดยฐานคำนวณไม่นับยอดที่ settle นี้เคยคืนไปแล้ว ตัวอย่าง: ปิด 900 (คืน 100, เก็บ savings 100) → แก้ 800 (เก็บ 200, ไม่คืนเพิ่ม) → แก้ 850 (เก็บ 150, ไม่ดึงคืน) → รีโหลดเห็น 850

  - **รอบ 4 (QA + กล้า) — สรุปกติกาปิดเคลมฉบับปัจจุบัน** (ใช้ฉบับนี้เมื่อขัดกับข้อความรอบก่อน) :
